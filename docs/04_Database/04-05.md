# 19. Table — Document Chunks

---

# 19.1 Purpose

The `document_chunks` table represents the smallest retrievable unit of knowledge within KnowledgeOS.

Instead of retrieving entire documents during Retrieval-Augmented Generation (RAG), the AI retrieves one or more semantically relevant chunks.

This approach provides:

- Faster retrieval
- Higher semantic relevance
- Better citation quality
- Lower token consumption
- Improved answer accuracy

Each chunk is tightly coupled to one parent document and one corresponding embedding stored inside ChromaDB.

The original document always remains the source of truth, while chunks serve as AI-optimized representations of the document's content.

---

# 19.2 Relationships

```text
profiles

│

└──────────── documents

                    │

                    │ 1 : N

                    ▼

             document_chunks

                    │

                    │ 1 : 1

                    ▼

               ChromaDB Vector
```

Each document contains multiple chunks.

Each chunk corresponds to exactly one vector record in ChromaDB.

Chunks never exist without a parent document.

# 19.6 ChromaDB Mapping

Each PostgreSQL chunk maps directly to one ChromaDB vector.

```text
PostgreSQL

Chunk

ID = 9fa2...

↓

ChromaDB

Vector ID = 9fa2...
```

KnowledgeOS generates chunk UUIDs before embedding generation.

The same UUID is used:

- PostgreSQL Primary Key
- ChromaDB Vector ID
- Citation Engine
- Retrieval Pipeline

This guarantees one-to-one synchronization between relational and vector storage.

Chunks preserve their original document order using `chunk_index`.

```text

↓

Chunk 1

↓

Chunk 2

↓

```

The ordering enables:

- Neighbor retrieval
- Context reconstruction
- Sequential citations
- Future summarization pipelines

# 19.9 Chunk Overlap

KnowledgeOS generates overlapping chunks to preserve semantic continuity across chunk boundaries.

```text
Chunk 1

──────────────────────

           overlap

                ▼

Chunk 2

──────────────────────
```

The overlap size is recorded using:

```text
overlap_tokens
```

Tracking overlap metadata allows future chunking strategies to evolve without requiring schema changes.

# 19.10 Source Metadata

Each chunk stores sufficient source metadata to support precise citations.

Citation metadata includes:

- Page number
- Paragraph number

- Heading hierarchy
- Chunk index

Example citation:


This enables explainable AI responses with fine-grained traceability.

---

# 19.11 Version Synchronization

Each chunk stores the same version number as its parent document.

```text
Document

Version 4

↓

Chunk

Version 4

↓

Embedding

Version 4
```

During embedding regeneration, newly generated chunks inherit the updated version value.

This version alignment allows the retrieval pipeline to validate that vectors correspond to the latest document state and prevents stale embeddings from participating in Retrieval-Augmented Generation (RAG).

# 19.12 Constraints

## Primary Key

```sql
PRIMARY KEY (id);
```

---

## Foreign Keys

```sql
FOREIGN KEY (document_id)

REFERENCES documents(id)

ON DELETE CASCADE;
```

If a document is permanently deleted, all associated chunks are automatically removed.

---

```sql
FOREIGN KEY (profile_id)

REFERENCES profiles(id)

ON DELETE CASCADE;
```

This guarantees complete user isolation.

---

## Self-Referencing Foreign Keys

```sql
FOREIGN KEY (previous_chunk_id)

REFERENCES document_chunks(id)

ON DELETE SET NULL;
```

```sql
FOREIGN KEY (next_chunk_id)

REFERENCES document_chunks(id)

ON DELETE SET NULL;
```

These relationships allow neighboring chunk retrieval while preventing circular deletion issues.

---

## Unique Constraints

Each chunk position within a document must be unique.

```sql
UNIQUE(document_id, chunk_index);
```

This guarantees deterministic ordering for every document.

---


```sql

```



# 19.14 Triggers

## Automatic Timestamp

```text
BEFORE UPDATE

↓

updated_at = NOW()
```

---

## Embedding Queue Trigger

Whenever a new chunk is inserted,

its initial status becomes

```text
pending
```

The embedding worker automatically detects pending chunks and begins embedding generation.

---

## Version Synchronization

Whenever a document version changes,

all existing chunks become obsolete.

The ingestion pipeline generates a completely new chunk set using the updated version number.

Old chunks are removed only after successful regeneration.

This prevents incomplete updates from affecting retrieval quality.

---

## Neighbor Link Generation

After chunk generation completes,

the backend automatically populates

- previous_chunk_id
- next_chunk_id

for every chunk.

Example

```text
Chunk 0

↓

Chunk 1

↓

Chunk 2

↓

Chunk 3
```

This enables efficient neighboring context retrieval.

## Regeneration

Whenever a document changes,

KnowledgeOS never edits existing chunks.

Instead,

```text
Old Chunks

↓

Marked Obsolete

↓

New Chunks Generated

↓

New Embeddings

↓

Old Chunks Removed
```

This guarantees retrieval consistency.

---

## Failed Embeddings

If embedding generation fails,

```text
embedding_status = failed
```

The retry worker periodically retries failed chunks.

Chunks marked as **failed** never participate in retrieval.

# 19.17 Neighbor Retrieval

KnowledgeOS retrieves neighboring chunks to improve context continuity.

Instead of returning

```text

```

the retrieval engine may expand to

```text
Chunk 17

↓

Chunk 18

↓

```

Neighbor expansion improves:

- Answer completeness
- Citation continuity
- Multi-step reasoning
- Hallucination reduction

The expansion window is configurable.

# 19.18 ChromaDB Synchronization

Each PostgreSQL chunk has exactly one matching vector.

```text
PostgreSQL

Chunk UUID

↓

ChromaDB

Vector UUID
```

Both systems store the same

- chunk_id
- document_id
- profile_id
- version

During retrieval,

the pipeline is capable of validating version consistency before assembling the final context.

If version mismatch occurs,

the vector is ignored until regeneration completes.

This prevents split-brain states between PostgreSQL and ChromaDB.

# 19.19 Design Decisions

## Why Store Chunk Metadata in PostgreSQL?

Relational metadata enables:

- Fast filtering
- Ordering
- Version tracking
- Citations
- Analytics

without querying the vector database.

---

## Why Store Chunk Text in ChromaDB?

Keeping chunk text alongside embeddings allows the retrieval pipeline to assemble prompt context immediately after similarity search without issuing additional database lookups.

This significantly reduces retrieval latency.

---

## Why One Chunk = One Vector?

A strict one-to-one relationship simplifies:

- Synchronization
- Deletion
- Regeneration
- Version control
- Citation mapping

---

## Why Immutable Chunks?

Immutable chunks eliminate synchronization issues.

Whenever a document changes,

KnowledgeOS regenerates an entirely new chunk set instead of editing existing chunks.

This greatly simplifies version management.

---

# 19.20 Business Rules

- Every chunk belongs to exactly one document.
- Every chunk belongs to exactly one authenticated user through its parent document.
- Every chunk has exactly one corresponding embedding stored in ChromaDB.
- Chunks never exist without a parent document.
- Every chunk stores the same version number as its parent document.
- Chunks are immutable after creation.
- Updating a document always generates a completely new chunk set.
- Chunks with `embedding_status = 'failed'` never participate in retrieval.
- Only chunks whose parent document has `processing_status = 'ready'` may participate in Retrieval-Augmented Generation (RAG).
- Soft-deleted documents immediately remove all associated chunks from retrieval through metadata filtering.
- Permanently deleting a document automatically deletes all associated chunks and their embeddings.
- Chunk ordering is preserved using `chunk_index`.
- Neighbor relationships are maintained for context expansion during retrieval.
- Chunk UUIDs are globally unique and reused as ChromaDB vector IDs.
- Every retrieval request is scoped by `profile_id`, ensuring complete tenant isolation.

# 19.22 Summary

The `document_chunks` table forms the core knowledge representation layer of KnowledgeOS and serves as the bridge between relational metadata and semantic vector search.

Each document is transformed into an ordered collection of immutable chunks, where every chunk maps directly to a single vector stored in ChromaDB. Rich metadata—including versioning, source location, heading hierarchy, token counts, and neighboring relationships—enables efficient retrieval, accurate citations, and high-quality context assembly for the RAG pipeline.

By separating structured metadata in PostgreSQL from embeddings and chunk text in ChromaDB, the architecture balances transactional consistency with high-performance semantic search. Version synchronization, immutable chunk generation, and one-to-one vector mapping ensure reliable operation even during document updates or embedding regeneration.

This design provides a scalable, production-ready foundation for Retrieval-Augmented Generation while remaining extensible for future capabilities such as adaptive chunking, multimodal ingestion, hybrid retrieval, knowledge graphs, and advanced AI-driven reasoning.
